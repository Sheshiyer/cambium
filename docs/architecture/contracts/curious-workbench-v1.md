# Curious workbench · visual and interaction contract

This local implementation applies the source-bound system atlas to the working
Curious browser and Telegram app. The atlas supplies a visual language; served
envelopes and verified server principals continue to supply facts and authority.

## Reference lock

| Reference | Adaptation | Limit |
| --- | --- | --- |
| `system-atlas-v1.md` and its shared renderer | Teal terrain, organ symbols, chartreuse selection, mint facts, peach held states, explicit rails | A symbol is a conceptual role, never a health indicator |
| `system-atlas-2026-10-07/index.html` | Clear hierarchy, bounded workbench, compact diagrams and progressive detail | Source diagrams cannot confer live readiness |
| Existing five-scene surface and Operating Fabric renderers | Mission, decision, tool, story and proof navigation; canonical cards and Task → Run → Receipt paths | Existing signed actions, exact joins and redaction remain authoritative |

## Decisions

- Use one shared palette with role-specific colors. Keep system fonts, a small
  type scale and a 4/8 px spacing rhythm; introduce no remote fonts or libraries.
- Bound the desktop workbench and give it a clear frame. Phones keep a full-height
  viewport, independently scrolling content, safe-area padding and reachable tabs.
- Organ imagery identifies the kind of work. Put counts and state labels next to
  their canonical facts. Never use illustration, motion or an empty list as proof.
- Present short scene summaries and primary cards first. Keep source, receipt and
  low-level rows in existing Inspect disclosures and contextual sheets.
- Give unavailable states usable read-only actions: retry the served route or
  inspect the source system. Authentication guidance does not invent a login URL,
  account role or owner approval.
- A failed, denied or empty ledger read invalidates all ledger-dependent panels
  and pending local detail. An older request cannot repaint after a newer request.
- Browser reads may use the existing verified Cloudflare Access founder path.
  Telegram reads carry runtime initData. Fabric activation still requires exact
  HTTP 200, `operatingFabricEnabled === true` and valid scene renderers. Browser
  viewer authority is unchanged and remains denied by the existing server.
- Gate decisions retain their server checks and explicit signed confirmation.
  UI state and URL parameters never grant a role or an enable flag.

## Acceptance surface

The canonical criteria live in `ISA.md` (ISC-2737–2768). Verify both owning shells
at desktop, 390 and 320 CSS pixels, with populated synthetic projection, empty,
authentication, service failure and offline states. Check navigation, sheets,
keyboard focus, zoom, reduced motion, scroll reachability and visible evidence.
Run the actual served-script harness and affected Worker/identity regressions.

The local preview must label its fixture responses and reject writes. Its source
data is synthetic and its API does not proxy production. Local screenshots prove
layout and interaction only. They do not prove an authenticated company identity,
Telegram signature validation, runtime health, deployment or device acceptance.
