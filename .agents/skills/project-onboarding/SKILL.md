# Project onboarding

Use `/project-onboarding <target>` in Cursor or Claude Code, or `$project-onboarding <target>` in Codex from the Cambium workspace. An explicit request to read and run this `SKILL.md` also works from another checkout. The same skill owns every client entry point. For an explicit `phases`, `waves`, `review-status`, `archive`, or `references` request, load [project entrypoints](workflows/project-entrypoints.md), resolve the one exact Thoughtseed project and run only the selected review. These targeted intents do not run the whole intake or grant effects. The existing `review` (default), `resume`, `roadmap`, `rails`, and `closeout` intents remain unchanged.

1. **Observe the project.** Resolve the exact WorkObject, client account, side project or repo; an ambiguous client name needs an explicit selection. Read the owning repo instructions, `PROJECT.md`, ISA and scoped handoff. Inventory the primary GitHub planning repo, associated repos and branches, and local source pins. Compare the Cambium Workbench projection with the Thoughtseed Labs registry and the repository’s current evidence. Keep verified GitHub identity, candidate membership and runtime admission separate. Use `npm run project:onboard -- <target> --github --out <label>` from Cambium; supply `--root`, `--repo`, `--primary`, `--vault`, `--board` and `--source` as needed. Read only selected sources.
2. **Review scope and prepare discovery.** Read the owning agreement register and exact executed agreement, exhibits and written amendments where available. Mark conflicting, draft, unsigned and missing evidence separately. Capture the local review using [runbook.md](runbook.md) and re-run with `--review`. Tailor all 30 questions and recommendations to the repo, brief, relevant requirements and applicable primary guidance. Where evidence is missing, state the gap in the recommendation. Ask the first three unresolved decisions that affect scope or acceptance. Use the host’s picker where available, preserve explicit deferrals, and resume from the last evidence fingerprint with `--progress`.
3. **Plan a reviewable roadmap.** For each proposed goal, cite its basis, exact spec/acceptance evidence, observable measure, pillar, dependencies and gate. Use the existing constitution and feature specs; if a repo has Spec Kit gaps, draft a traceable spec and plan in its existing layout. Keep client changes separate from proposed product improvements. GSD owns finite work and ISA owns acceptance. Reuse the exact private GitHub board, or prepare a scoped creation proposal if none is confirmed. Apply only the reviewed changes under the current request and the owning GitHub contract.
4. **Plan the project chats.** Load [Phases and waves](workflows/phases-and-waves.md). Reconcile the roadmap and current phase before proposing chat names and parent relationships. Assign pillars as owners of work within a phase or wave. This intake chat hands project execution to the owning project chat.
5. **Review and close.** Load [Scheduled review](workflows/scheduled-review.md) for a standing read-only review and [Archive](workflows/archive.md) to reconcile finished children. A dry run produces local review and archive proposals. Use the exact project’s existing tools for authorized live actions.
6. **Record related design evidence.** Load [Cross-project references](workflows/cross-project-references.md) for source inventory and proposed reuse. Route a deeper design review to its own chat when requested.

For a Sapling, use the [product discovery track](runbook.md#sapling-product-discovery). Replace commercial scope assumptions with dated market and user evidence, a founder-owned measurable goal, and an experiment with a stop rule. Trace source → goal → story → flow → scenario proof → measure. An explicit `--track sapling` can prepare a separate product hypothesis using a Branch’s sources without changing its identity or delivery roadmap.

For requested host setup or migration, follow [workspace mapping across hosts](runbook.md#workspace-mapping-across-hosts) before opening pillar chats.

Use [runbook.md](runbook.md) for exact GitHub and chat operations, local data formats, integration boundaries and a reusable recurring review prompt. Keep raw agreements, commercial terms, private chats and credentials in the authorized source; project only the minimum approved facts and links.
