# The first session — a 20-interaction ethical tutorial

This document is the experience contract for teaching Cambium's infinite loop. It is not a transcript of the current production UI. Each interaction is labelled by its current evidence level so designed behavior cannot be mistaken for live behavior.

Fitcheck is the reference story threaded through the Workbench and Telegram Mini App. See the [golden path](./docs/architecture/fitcheck-golden-path.md).

## Motivation without manipulation

| Drive | Ethical use in Cambium |
|---|---|
| 1 · Epic meaning | connect a project to its durable cause |
| 2 · Accomplishment | show only evidenced progress |
| 3 · Creativity and feedback | let the founder propose one reversible change and see consequences |
| 4 · Ownership | make identity, authority, and decisions legible |
| 5 · Relatedness | ground work in real customers and accountable collaborators |
| 6 · Scarcity | show actual time, spend, or solvency bounds only |
| 7 · Curiosity | reveal meaningful evidence and uncertainty |
| 8 · Loss avoidance | warn only when a real viability or integrity boundary is threatened |

White-hat drives carry the experience. Scarcity and loss may appear only when backed by real data. There are no fake countdowns, streak traps, mystery rewards, or manufactured emergencies.

## Noesis and the mid-brain axis

Epic meaning and existential loss are not routine workflow states. They invoke noesis: the higher-order reflection that reconnects the move to purpose and, when necessary, returns authority to the human.

The tutorial has exactly three noesis peaks:

1. **Interaction 1 · The Calling** — why this project deserves to exist.
2. **Interaction 18 · Do not drop out** — a real boundary is threatened.
3. **Interaction 20 · The game continues** — evidence returns to purpose rather than engagement pressure.

All other interactions remain inside the normal micro/meso/macro control stack.

## How the two UIs teach the loop

### Workbench

The Workbench begins with identity and provenance. For Fitcheck, the Operate tab presents the packet story, mission/KPI targets, candidate organ route, gate ledger, lifecycle ladder, and explicit holds. It is the place to reconcile and prepare a proposal.

### Telegram Mini App

The Mini App begins with the present operational context. Mission, Flow, Workforce, Forge, Gate, and Inspect progressively reveal the same Fitcheck contract. Runtime joins are exact WorkObject joins; packet owners are not called live assignments; organ hints are not called pinned loadouts; a packet gate does not render an action button.

### Shared rule

The UI may celebrate a stage only when its owning authority supplies evidence. If D1 contains an exact Fitcheck WorkObject anchor, `ADMITTED` may become evidenced. It must not unlock `PINNED`, `EXECUTED`, or `LEARNED` without their separate proofs.

## Guardrails

- Never convert an alias into runtime identity.
- Never display a target KPI as an achieved metric.
- Never call packet planning a live assignment.
- Never call organ hints a loadout pin.
- Never call a prepared action an approval.
- Never call synthetic foldback a production run.
- Never expose private prompts, secrets, native session identifiers, or machine-local paths.
- Never optimize for time-in-app; optimize for a clearer, safer next decision.

## Completion test

The tutorial is successful when a founder can answer, without guessing:

1. What project is this?
2. What is planned?
3. What is operationally admitted now?
4. What is still held, and by which authority?
5. What one change could enter Gate next?
6. What evidence would return after execution?
7. Why can that evidence inform, but not silently commit, the next intent?
