# Plan 02-01: Telegram Operator Intake

## Objective

Expose the proven synthetic, internal-only service-agreement draft through the existing allowlisted Hermes Telegram plugin, with deterministic D1 replay and a redacted status receipt that needs neither JSON, coding CLI, SSH, artifact bytes, nor the runner member credential.

## Deliverable Manifest

| ID | Deliverable | Acceptance |
|----|-------------|------------|
| D1 | Cambium operator receipt | additive source provenance, explicit safe DTO, assignment/admin/member auth matrix, raw read authority unchanged |
| D2 | Hermes draft command | default-off registration, fixed synthetic payload, stable daily replay, truthful receipt, outcome-unknown reconciliation |
| D3 | Hermes status command | strict task-ID parser, safe GET client, validated state/artifact output, no raw JSON or internals |
| D4 | Versioned releases | full suites, clean commits, backward-compatible Worker-first deployment, retained rollback versions |
| D5 | Live operator proof | registered commands, founder/group allowlist, one task/artifact, replay counts, health, rollback, revoked SSH |

## Tasks

1. Add `hermes-telegram-operator` as an additive business-intake source and implement the allowlisted operator receipt endpoint in Cambium.
2. Prove assignment/admin/member access to the receipt while retaining assignment-token 403 responses for raw task and artifact endpoints.
3. Add the feature-gated `/ts-agreement-draft` and `/ts-agreement-status` handlers, exact payload/replay rules, safe HTTP clients, redaction, and failure wording to Hermes.
4. Register both commands only when `HERMES_SERVICE_AGREEMENT_OPERATOR_ENABLED=true`, document them in `/ts-help`, and test enabled/disabled command registries.
5. Run focused and full suites in clean worktrees; commit release candidates with captured source identities.
6. Capture live deployment and allowlist baselines, deploy the backward-compatible Worker, then deploy Hermes with the feature disabled.
7. Rehearse one-version Hermes rollback, audit D1 for orphans, restore the new release, enable the command, and prove gateway health and registry readback.
8. Invoke the deployed handler with gateway-scoped configuration, verify one D1 task reaches awaiting human approval, inspect the redacted status, replay it, and compare D1/R2 counts.
9. Disable or retain the feature according to proof outcome, record GSD/ISA evidence, verify services, and revoke temporary SSH ingress.

## Checkpoints

- CP1: The redacted DTO uses an explicit field allowlist and never spreads the raw task or artifact response.
- CP2: Existing raw task/artifact assignment-token denial remains green.
- CP3: The command constructs its UTC-day envelope once; retries cannot cross into a different key or approval observation.
- CP4: A 409 never changes keys; exhausted transport reports outcome unknown and gives the deterministic status task ID.
- CP5: Command registration is off by default and activated only after founder/group allowlist metadata is verified.
- CP6: Worker deploys before Hermes and remains compatible with the previous Hermes source.
- CP7: The live task remains synthetic, externalAction none, and awaiting human approval; any send/sign/delivery behavior aborts.
- CP8: Temporary SSH ingress is revoked even on failure.

## Rollback

- Set `HERMES_SERVICE_AGREEMENT_OPERATOR_ENABLED=false` and restart the gateway; runner execution remains unchanged.
- Restore `/opt/hermes-aws-ts` from the deploy script's retained previous release if plugin health regresses.
- Retain the additive Worker endpoint; redeploy Worker version `108f7550-2a5a-43ea-bff4-6aefd6716988` only if the new Worker is unhealthy.
- Leave completed synthetic tasks immutable; conditionally delete only a proven claim-free, execution-free, artifact-free failed canary.
